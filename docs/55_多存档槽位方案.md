# docs/55 · 多存档槽位（同一世界多结局并行）方案

> 目标：让玩家在同一个世界里开**多个独立存档**，互不覆盖；游玩中途可把当前进度**另存为新存档**（分叉新线），从而同时推进多条结局线。
> 关联：docs/54（规则可视化与结局系统）无依赖，可独立落地。

---

## 1. 为什么现在"只能一个存档 / 会被覆盖"

根因只有一个函数：`src/save.js::createOrUpdateSave()`（第 205 行）

```js
const existing = S.saves.find(s => s.worldId === S.currentWorld.id); // ★ 按"世界"找
```

- `S.saves` 本就是**数组**，每个存档已有独立 `id`、`worldId`、`worldName`、完整运行时字段（state/history/lore_kb/…）。数据结构、存储方式（IndexedDB 单 key 存整个数组）**都不用改**。
- 但因为"按世界找"，每个世界永远只有一条存档，每次保存都覆盖那条 → 表现为"存一个覆盖另一个、不能同时玩多结局"。
- 连带问题：`continueLatestSave(worldId)`（save.js:103）按 worldId 取唯一档；世界详情"开始游玩/继续游戏"分流（render.js:623-644）一旦有存档就只能"继续"，想重开新线只能先删旧档。

**结论：底层已支持多存档，只差"按槽位读写 + 另存为新槽位 + 选择入口"。改动小、风险低、对旧档零破坏。**

---

## 2. 数据模型变更（极小）

### 2.1 `S.currentSession` 增加 `saveId`
`src/store.js:39`：
```js
currentSession: { epoch: 0, worldId: null, saveId: null },  // ★ saveId 绑定当前游玩会话到具体槽位
```
作用：游玩会话（自动存档、手动保存）永远只写**当前槽位**，不再波及同世界其他槽位。

### 2.2 存档对象新增可选 `name`（槽位名）
`createOrUpdateSave` 新建时写入 `name`；旧档无 `name` 时 UI 回退显示 `世界名 · 进度`。
- 不引入新必填字段，`save.js` 其余字段不变 → 旧档读取完全兼容。

## 3. 改动清单

### 3.1 `src/store.js`
- `currentSession` 增加 `saveId: null`（见 2.1）。

### 3.2 `src/save.js`
| 函数 | 改动 |
|---|---|
| `createOrUpdateSave()` | 改为按 `S.currentSession.saveId` 定位：`existing = S.currentSession.saveId ? S.saves.find(s=>s.id===saveId) : null`。命中则更新该槽位；未命中则**新建**槽位（`id:"s"+Date.now()`、`saveId` 同步、写 `name`），`unshift` 进 `S.saves`。删除"按 worldId 找"逻辑。 |
| `saveAsNewSave(name)`（新增） | 把当前运行时（gameState/history/chatHistory/lore_kb/behavior_records/player_notes…）深拷贝成**新存档对象**，生成新 `id`，`name = name||默认名`，`unshift` 进 `S.saves`，`S.currentSession.saveId = 新id`，`saveSaves()` + `saveState()`，toast「已另存为新存档：<名>」。 |
| `startGame(opts)` | 进入新周目前：`S.currentSession.saveId = "s"+Date.now()`（生成全新槽位 id），使"开始游玩/开新存档"永远创建新档、**不覆盖**任何已有档。后续 `createOrUpdateSave` 因 id 不存在而新建。 |
| `loadSave(saveId)` | 进入后 `S.currentSession.saveId = saveId`（关键：绑定会话到所读槽位，之后自动存档只更新它）。 |
| `continueLatestSave(worldId)` | 取该世界最近 `lastPlayed` 的档；存在则 `loadSave(该档.id)`；若无档则 `startGame` 开新档。 |
| `deleteSave(saveId)` | 删除后：若 `S.currentSession.saveId === saveId` 则置 `null`（避免悬空）。其余不变（已按 id 删）。 |

### 3.3 `src/render.js`

## 4. UX 流程（已与用户确认的两处设计）

1. **世界详情多存档入口（弹窗）**：一个世界有 ≥2 存档时，点「继续游戏」弹出**存档选择弹窗**——列出该世界全部存档（继续/删除）+「＋ 开新存档」；仅 1 档时仍直接继续（体验不变）。
2. **游戏内保存菜单**：游戏顶栏「保存」按钮 → 菜单含「保存当前档」「另存为新存档（可命名）」。当前档仍保持每回合自动保存；「另存为」随时分叉新线。

### 典型场景
- 玩到「好结局」前点「另存为新存档：好结局线」→ 继续推进触发好结局；之后回世界详情选原档玩「坏结局线」→ 两线互不覆盖。
- 存档列表页同一世界出现多条，带槽位名区分。

## 5. 边界与兼容性

- **旧档兼容**：旧存档无 `saveId`/`name`；读档按 `id` 本就匹配，点继续自动绑定 `S.currentSession.saveId`，之后自动存档只更新该档，不影响其他（若以后有多个）。`name` 缺失 UI 回退 `世界名 · 进度`。
- **自动存档安全**：每回合 `createOrUpdateSave` 现在只写 `S.currentSession.saveId` 对应槽位，彻底杜绝跨槽位覆盖。
- **删当前档**：`deleteSave` 清 `saveId`，下次进该世界走「开新存档/选档」流程，无悬空引用。
- **孤儿存档**：世界已删的存档（render.js:434 `worldMissing`）逻辑不变，仍可查看/删除。
- **`startGame` 不再覆盖**：即使世界已有存档，点「开始游玩/开新存档」都生成新槽位 id，旧档保留。

## 8. 风险

- **低**：不改动存档数据结构与存储层；旧档零破坏；核心只换"定位键"+"另存为"两件事。
- 唯一注意：所有"自动存档/手动保存"路径必须确保 `S.currentSession.saveId` 已被正确设置（startGame/loadSave 两处已覆盖），否则会退化成"新建空档"。测试第 1、7 项专门卡这点。
