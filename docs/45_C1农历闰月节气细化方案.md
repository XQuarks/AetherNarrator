# C-1 农历闰月/节气细化 · 实施方案

> 状态：方案待黎总确认范围（2026-07-29）
> 依据：docs/34 §未完成（C-1「农历闰月/节气显示细化」P2 ⬜）、docs/38 §五（C-1 农历节气细化）
> 定位关键词：**「显示细化」**——不是重写农历算法。

## 1. 现状（已核实代码，非记忆）

- `lunar` 模式是**解耦的简化农历**：`current_date = {year, month(1–12 索引 DEFAULT_LUNAR), date}`，月名固定 正月…腊月，大小月 30/29 交替（约 354 天/年）。
- **没有节气**：`DEFAULT_LUNAR` 与 `formatCalendarDate` 里均无 节气 字段。
- **没有闰月**：`addLunar` 按固定 12 月表进位，`month` 超 12 会回绕；闰月目前只能走 `custom_calendar` 的「闰X月条目」机制（docs/35 已有 `insertLeapMonth` + 命名 `闰X月`）。
- `node_modules` 无 `lunar-javascript` 等真实农历库；本项目的农历就是内置静态表，与方案 B「时间系统彻底解耦」哲学一致。

## 2. 目标

- 古风/仙侠世界用 `lunar` 模式时，日期显示**带上周遭节气**，AI 也能感知节气推进剧情（清明、冬至等）。
- 需要闰月的世界有**现成、零算法风险**的实现路径，不踩日期进位 bug。

## 3. 推荐范围 A（轻量 · 显示标注 · 无新依赖）

### A-1 节气显示（核心，必做）
- 新增 `src/calendar.js::SOLAR_TERMS`：12 农历月 → `[节, 中气]` 标准映射
  （正月→立春/雨水、二月→惊蛰/春分…腊月→小寒/大寒）。
- `formatCalendarDate(cd, "lunar", custom, { showSolarTerms = true })`：lunar 分支在月名后附加「· 立春～雨水」。
- 透传：在 `src/theme.js` 的 `formatDateOnly` / `formatWorldTime` / `formatDeadlineLabel` 默认开启 `showSolarTerms`（不影响 gregorian/custom 输出）。
- `src/prompt.js` lunar 分支：在给 AI 的日期说明里补「当前农历月对应节气：X～Y」，便于剧情借节气起承转合。
- 测试 `test/45-c1-lunar-solar-terms.test.js`：表正确性 + 格式串（含/不含节气）+ prompt 注入串。

### A-2 闰月标注（复用 custom_calendar · 零算法风险）
- 新增 `src/calendar.js::CUSTOM_CALENDAR_PRESETS.lunarLeap`：含「闰二月」的 13 月农历示例表，创作者一键载入「农历（含闰月）」模板。
- `src/lore-ui.js` 农历/自定义 编辑器加提示文案：「需要闰月的世界，请改用『自定义历法 · 农历(含闰月)』模板，并在月历表插入闰月」。
- **不做**：lunar 模式自身加闰月（会与 12 月进位冲突；且某年是否有闰X月取决于年份，需 per-year 数据，超出「显示细化」范围）。

## 4. 明确不做的边界

- ❌ 不引入 `lunar-javascript` / 真实农历格里历换算（与方案 B 解耦冲突、需 vendor 本地化、改动大）。
- ❌ 不重写 `lunar` 进位算法。
- ❌ 节气精确到「日」需要格里历锚点，decoupled 农历无锚点 → 只给「月对应两节气」，不给具体落日（这是显示细化，不是天文计算）。

## 7. 备选范围 B（不推荐）

引入 `lunar-javascript` 真实农历引擎，让 `lunar` 模式基于真实公历算闰月 + 节气精确到日。改动大、与解耦哲学冲突、需新增 vendor 依赖。除非你要的是「真实农历」，否则走 A。
