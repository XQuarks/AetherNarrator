# docs/57 · 知识库运行时双轨更新方案（推荐方案 B）

> 状态：✅ 已实施（2026-08-03，方案 B 全部落地；用户拍板：复用 B7 / 偏离报告进 v1 / 不做回滚按钮 / 仅改已有+可新增本局事实）
> 关联：对话背景——玩家分支行为（如开局杀死哈利波特）是否应反映进知识库；前序风险：① 静态 lore 仍被召回导致矛盾、② 裁判(critic)比对静态 lore 误判违和。

---

## 0. 要解决的问题

知识库（lore）当前是**作者写死的静态设定书**：游玩只读取、不回写（`rag.js::retrieve` 全程只读 `getWorldLoreKB()`，无任何写回逻辑）。

这导致两个真实问题：

1. **矛盾召回（风险①）**：玩家开局杀死哈利后，lore 里"哈利是救世主、第七部打败伏地魔"等卡片仍可能被 RAG 召回注入，与"哈利已死"打架。
2. **裁判误判（风险②）**：`llm.js::getWorldLoreForJudge` / `judgeWorldviewConsistency` 拿**静态 lore** 当尺子量叙事，会把合理的分支（提前杀哈利）判成"违和/违规"。

用户诉求：让 AI 判断本局剧情相对知识库改了多少，据此产出内容并"更新知识库"，类似"更新一条实际发生的时间线"。

---

## 1. 核心原则：原著不可变，存档工作副本可变（双轨）

项目里**已存在天然落点**：

- `currentWorld.lore_kb` —— 作者原著（资产），**游玩中永不写入**。
- `S.activeLoreKB` —— 每存档独立的 lore 工作副本（B7 设计，开局从原著深拷贝）。**这就是"可变的知识库"**：只改这个副本，原著安全。
- 重置存档 / 开新存档 → 重新从原著深拷贝生成工作副本，干净如初。

再补一个**透明流水账** `S.worldRuntime.deltaLog`：记录本局所有"相对原著的改变"，纯展示 / 回滚用。

> 选「改工作副本」而非「平行覆盖层 + 检索压制」的关键好处：`rag.js::retrieve()` 读的是 `getWorldLoreKB()` → `activeLoreKB`，工作副本一更新，**RAG 自动生效、无需额外压制逻辑**，实现更简洁、漂移风险更低。

---

## 2. 数据模型

```js
// store.js · S.worldRuntime（随存档持久化，不污染 world 对象）
S.worldRuntime = {
  deltaLog: [                       // 每回合 AI 产出的结构化差异
    { turn: 1, entity: "harry", field: "alive",
      from: true, to: false, reason: "开局被玩家杀死" }
  ],
  entityStates: {                   // 实体状态快查表，便于 UI 与裁判读取
    harry: { alive: false, deathTurn: 1, reason: "开局被玩家杀死" }
  }
}
```

- `deltaLog` 与 `entityStates` 可由 `lore_delta` 同构推导，二者互补：deltaLog 管"历史流水"，entityStates 管"当前快照"。
- 重置 / 新开：清空 `worldRuntime`，`activeLoreKB` 从 `currentWorld.lore_kb` 重新深拷贝。

---

## 3. AI 契约扩展（几乎零额外成本）

`game.js::processTurn` 里 AI **已经**返回结构化 `state_changes` / `key_facts`（由 `applyStateChanges` 消费）。在同一响应里**新增一个字段 `lore_delta`** 即可，不增加 LLM 调用次数：

```json
{
  "lore_delta": [
    {
      "op": "override",
      "lore_id": "harry_alive",
      "field": "content",
      "patch": "哈利·波特已于第一回合被玩家杀死，预言另寻承载者。",
      "note": "开局击杀分支"
    }
  ]
}
```

- 由新函数 `applyLoreDelta()` 写入 `S.activeLoreKB` 对应片段，并 push 到 `deltaLog` / 更新 `entityStates`。
- **只 append / replace，永不删除原著卡片**，且每条 delta 可回滚。
- 被改动的片段触发 `ensureLoreEmbeddings` **局部重算向量**（仅变动项，非全量）。

## 5. 完整例子：开局杀哈利

1. 玩家输入"一记魔咒击杀哈利"。
2. AI 响应：`state_changes`（玩家无关）+ `lore_delta:[{override harry_alive ...}]`。
3. `applyLoreDelta` 把 `activeLoreKB` 里哈利相关片段 `content` 改为"已死"，push `deltaLog`、更新 `entityStates`。
4. 之后 `retrieve()` 召回的就是"哈利已死"版本 → **无矛盾（风险①解决）**。
5. 裁判拿到 `worldRuntime`，知道"哈利死了是本局事实"，不再误报违和（**风险②解决**）。
6. 侧栏"偏离原著"面板显示：哈利（存活 → 死亡）@ 回合 1。

## 7. 边界（明确不做）

- **不改 `currentWorld.lore_kb`**（原著资产保护）。
- v1 不做跨存档共享覆盖、不做 LLM 全自动"重写整本设定书"（防设定腐化 / lore rot）。
- 不影响防剧透门禁（`unlock_stage`/`story_progress` 逻辑保持独立，delta 改写后门禁仍按阶段生效）。

## 附录：替代方案（平行覆盖层 + 检索压制）

若不写工作副本，也可在 `rag.js::retrieve()` 末尾加一层：凡 `lore_id` 命中 `worldRuntime.factOverrides` 的片段，drop 或替换其 `content`，原文案 `activeLoreKB` 不动。
- 优点：原著副本与运行时彻底分离，回滚更干净。
- 缺点：需额外维护 override 表 + 检索期匹配，且要同步处理向量（被替换内容也需重算向量），复杂度高于直接写工作副本。
- 当前推荐**直接写 `activeLoreKB`**（见 §1），本附录仅作备选记录。
