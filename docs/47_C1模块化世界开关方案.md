## 1. 它是什么

让**创作者决定本世界启用哪些系统**（时间/技能/背包/好感度/变量/目标……）。三大作用：

1. **约束 AI**：关闭的系统，系统提示里明确告诉 AI「不要自行引入相关机制」，减少乱编货币/商店/任务。
2. **控制 UI**：关闭的模块，状态栏对应页签自动消失。
3. **控制逻辑**：关闭的模块，引擎不应用对应状态变化（好感度/变量/物品/目标/时间推进）。

---

## 2. 设计：模块注册表（Registry）模式 ⭐

核心思想：把"本世界启用哪些系统"抽象成统一的**模块描述对象**，集中登记在 `src/modules.js` 的 `MODULE_REGISTRY`。开关 UI、提示词注入、状态 Tab 显隐、逻辑门禁**全部从该表自动派生**。以后新增一个可开关系统 = 往表里加一条描述，几乎不动业务代码。

```
MODULE_REGISTRY（单一真相源）
   ├─ 提示词注入   buildModulePromptContext(world)   → 启用指令 + 未启用约束
   ├─ 状态 Tab 显隐 renderStatusTabs()              → 只显示启用模块的页签
   ├─ 逻辑门禁     applyStateChanges()               → isModuleEnabled 问同一函数
   └─ 编辑器 UI    renderModuleSwitches(world)       → 按注册表自动渲染勾选框
```

模块描述字段：`id` / `name` / `desc` / `defaultEnabled` / `core`(不可关) / `statusTab`(状态栏页签) / `promptFragment(world)`(启用时注入的行为指令)。

存档结构：`world.modules = { time:{enabled:true}, variables:{enabled:false}, ... }`。

三个全局复用工具：`defaultModules()`（新世界默认）、`sanitizeModules(world)`（旧世界迁移/读档兜底）、`isModuleEnabled(world, id)`（所有门禁统一问它）。

## 5. 加一个新模块有多简单（易扩展性证明）

以"任务系统 quest"为例，本期已实现业务只需：
1. 在 `src/modules.js` 的 `MODULE_REGISTRY` 加一条 `{ id:"quest", name:"任务系统", defaultEnabled:false, statusTab:"quest", promptFragment:()=>"【任务系统】…" }`；
2. 写任务业务自身逻辑（接 `isModuleEnabled(world,"quest")` 门禁）。

**开关 UI、提示词注入、状态 Tab 显隐、存读档/迁移全部自动**，无需改 render.js / prompt.js / storage.js / app.js。对比散装写法（每个系统改 5+ 文件），接入成本归零。

## 7. ⚠️ 行为提示（需你拍板是否调整）

按确认的默认，`affinity`（羁绊好感度）**默认关闭**。后果：
- 新创建的世界、以及经迁移的旧世界/三个演示世界（克苏鲁/都市传说/双世界），好感度均**默认不生效**，需在世界详情 → 「模块开关」里手动打开「羁绊好感度」。
- 这是"开箱无数字压力"的一致体现，但会改变已落地 B4 好感度的默认表现。
- 若你希望**演示世界保留好感度**，可把 `affinity` 的 `defaultEnabled` 改为 `true`（一行），或仅在演示工厂函数里显式开启。要我改吗？
