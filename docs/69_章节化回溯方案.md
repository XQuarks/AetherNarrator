> 核心结论：**纯事件溯源（重放事件重建状态）在 LLM 游戏里不可行**（AI 的 state_changes 不幂等、依赖当轮上下文，重放必然漂移）；改用**「每回合状态快照 + 历史截断」**的轻量事件溯源——可靠、实现简单、与现有存档天然兼容。

## 一、需求与目标（B5'）

玩家玩到第 20 回合，想**回到第 10 回合重新选择**（后悔药/体验另一条线/回看剧情节点）。要求：
1. 任意历史回合可回退，恢复**当时的游戏状态 + 当时的对话**；
2. 回退后从该点继续游玩（时间倒流，时间系统方案 B 已允许倒流，无冲突）；
3. 想保留"原未来线"时，可先**另存为新存档**再回退（= 分支，复用 docs/55 多存档）；
4. 旧存档无回溯记录时给出友好提示（从现在开始记录）。

## 二、为什么不做"纯事件重放"（关键设计决策）

WorldLines 的事件溯源建立在**确定性世界状态机**上（每个事件确定性地改变状态）。但 AetherNarrator 的 `gameState` 由 LLM 每轮输出 `state_changes` 增量驱动——LLM 生成**不幂等**：同样输入在不同轮次可能给不同增量，且增量依赖当时的完整上下文。若只存"状态变更事件"再重放：
- 重放到第 N 回合，得到的状态与当时真实状态必然漂移；
- 需要重跑 LLM 才能对齐，等于重新生成一遍剧情（失去"回溯"意义）。

→ **正确做法：每回合保存一份轻量状态快照（gameState）+ 该回合对话条目**。回溯 = 取目标回合快照恢复状态 + 从现有对话历史截断到该回合。快照是可靠锚点，事件条目提供历史切片，二者结合即"可回溯的章节"。

## 三、现状盘点（为什么改动很小）

| 现状 | 说明 |
|---|---|
| 每回合自动存档 | `save.js::createOrUpdateSave`（game.js processTurn 定稿后调用），存档含完整 `state`（gameState）+ `history`（conversationHistory 全量）+ `chatHistory` + `chatSummary` + `behavior_records` + `world_runtime` 等 |
| 多存档槽位 | docs/55 已落地：`S.currentSession.saveId` 绑定槽位；`saveAsNewSave` 分叉新线；同世界多档并存 |
| 回合结构 | `conversationHistory` 条目 `{player, narrative, choices, retrieved, period, day, tcd, key_facts, atmosphere, varChanges, state_changes, ...}`；`chatHistory` 为 LLM 轻量消息（约 2 条/回合） |
| 时间倒流 | docs/20/21 方案 B：时间倒流允许，`current_date` 无隐藏序数 → 回溯改日期无机制冲突 |
| 状态面板 | 已有「timeline」tab（世界时限/NPC 动态/事件进度）可挂回溯入口 |
| 存储 | IndexedDB 单 kv store（idb.js），key 字符串，容量远超 localStorage |

→ 结论：**回溯需要的"历史切片"在存档里本来就有**（history 是连续的）；只缺"任意回合的 gameState 快照"。补一个**回合日志**即可。

## 四、数据模型：回合日志（新增，随存档槽位）

```jsonc
// IndexedDB key: "aigame_log_" + saveId （新建独立 key，不动现有存档结构）
{
  "schema_version": 1,
  "saveId": "s1723000000000",
  "worldId": "w1",
  "turns": [
    {
      "turn": 1,                    // 该回合结束时 conversationHistory.length
      "t": "2026-08-07T10:00:00",   // 时间戳（展示用）
      "label": "第1天·早晨",          // formatWorldTime 摘要
      "state": { ... },             // ★ gameState 深拷贝（该回合定稿后）
      "entry": { "player": "...", "narrative": "...", "choices": [...] },  // 该回合对话条目（展示摘要用）
      "chat_tail": 4                // 该回合后 chatHistory 条数（回溯时截断 chatHistory 用）
    }
  ]
}
```

**规则**：
- **追加时机**：正常玩家回合定稿后（`applyNormalTurn` 结尾 / `createOrUpdateSave` 前），同步追加一条；`isComm`（通讯）/警告/系统提示等不入日志；
- **容量上限**：`MAX_TURNS = 500`，超出后丢弃最旧（slice(-500)）——500 回合 × (state ~5KB + entry ~2KB) ≈ 3.5MB，IndexedDB 可承受；
- **独立 key**：不污染 `S.saves` 数组，旧档读取逻辑零改动；
- **另存为新存档**（`saveAsNewSave`）：复制当前日志为新槽位 key（`aigame_log_<新id>`），新线从复制点继续记录——天然分叉；
- **删除存档**：连带删除对应日志 key。

## 五、回溯执行流程（核心逻辑，纯函数可测）

`rewindToTurn(save, log, targetTurn)` 返回新的运行时数据：

1. 校验 `targetTurn ∈ [1, log.turns.length]`；取 `snap = log.turns[targetTurn-1]`；
2. `S.gameState = deepClone(snap.state)`；
3. `S.conversationHistory = save.history.slice(0, targetTurn)`（存档 history 连续，直接截取；用 `snap.entry` 与第 targetTurn 条校验一致性，不一致则拒绝并提示）；
4. `S.chatHistory = save.chatHistory.slice(0, snap.chat_tail)`（截断到该回合的消息数）；
5. `chatSummary` 保留（前情提要摘要仍有效；如需更精确可后续用 `rebuildSummaryFromHistory` 重建——见风险节）；
6. `behavior_records / world_runtime / lore_kb / player_notes / ai_enhanced` **保留现状**（记忆与知识不因回溯丢失；"记忆保留 or 清空"做成选项，默认保留）；
7. `createOrUpdateSave()` 覆盖当前槽位（未来线被覆盖——**UI 强提示：想保留原线先「另存为新存档」**）；
8. 清空当前回合锁、重渲染（renderLog / 状态面板 / 时间线）。

**为何可靠**：快照是当时真实状态（非重放推演）；history/chatHistory 截断是纯数组操作；唯一"重建"是 gameState 替换，无 LLM 参与。

## 七、UI 设计（回溯面板）

- 入口：状态面板 → timeline tab →「⏪ 章节回溯」按钮；
- 面板：时间线列表（最近 50 条，倒序），每条显示 `label + 玩家输入摘要 + 选项数`；顶部显示「记录 N 回合」；
- 点某条 → 确认弹窗：
  - 说明「将回到 第 X 回合（label），其后 Y 个回合将被覆盖」；
  - 两个按钮：「仅另存为新存档」（先分叉再自动回溯，保留原线）/「直接回溯」（确认覆盖）；
- 回溯后 toast「已回到 第 X 回合」+ 渲染截断后的对话（更早的回合保留在日志里可再次回溯）。

## 九、兼容与风险

- **旧档**：无 `aigame_log_<saveId>` → 面板显示「该存档暂无回溯记录，从现在开始记录」（第 1 回合起追加）；读档流程零改动；
- **性能**：每回合多 1 次 IndexedDB 写（~5-7KB），可与 `saveState` 批量写合并（idbSetMulti），影响可忽略；
- **风险 1**：`chat_tail` 与 history 截断不一致 → 用 `snap.entry` 与 history[targetTurn-1] 做一致性校验，不一致拒绝并提示；
- **风险 2**：`chatSummary` 在回溯后可能包含"未来"信息 → 一期保留（摘要粒度粗、影响小）；二期可用 `rebuildSummaryFromHistory` 重建；
- **风险 3**：回溯覆盖未来线 → UI 强提示 + 一键另存为保护；
- **风险 4**：日志膨胀 → MAX_TURNS 500 + 超限丢弃最旧。
